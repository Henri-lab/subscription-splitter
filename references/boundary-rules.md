# 拆分判据（boundary rules）

> 每一刀都要过这里。默认答案是"**不拆**"——拆的人负责举证收益。

## 1. 拆分四问（按顺序，任一答不出就停）

1. **时间属性**：它是不变事实、派生状态、负债，还是触发器？
2. **一致性边界**：这个不变量必须和谁同事务成立？（跨边界 = 把推导变分布式计算）
3. **拆分收益**：这刀换来什么——独立扩缩容？团队边界？部署节奏？写出来，量化。
4. **拆缝**：跨边界的交互是否走事件/outbox（INV-18/19），还是同步调用补一致性（禁止）？

## 2. 一致性边界表（默认配置）

| 边界 | 成员 | 为什么必须在一起 |
| --- | --- | --- |
| 交易边界 | 订单 + 支付 + 权益（+会员视图） | "支付成功"与"权益开通"必须同事务；裂开 = 钱收了货没给 |
| 负债边界 | 积分账本 | 账只能追加，余额是 Σ delta 的派生；与交易边界靠事件耦合 |
| 调度边界 | 订阅触发器 + 提醒策略 | 它只是交易边界的"自动水龙头"，不是数据主人 |
| 身份边界 | 认证（ASP） | 只发 principal，与业务边界解耦 |

## 3. 三个灵魂拷问（拆分方案的验收）

1. **"付了钱但会员没开通"发生在哪一格？** —— 支付（事实）与权益（派生）之间裂开。若你的拆分把这两格放进两个服务/两个事务，这就是事故现场。
2. **积分余额能像会员状态一样 UPDATE 吗？** —— 不能。会员是缓存可重建；积分是负债，UPDATE = 销毁凭证，只能追加流水。
3. **会员过期那一刻发生了什么？** —— 什么都没发生。无事件、无 UPDATE，只是"现在"越过了"有效期"。若你的设计给会员过期写了一条"过期事件 + UPDATE"，说明你把它当成了状态机而不是投影。

## 4. 正反例

### 反例：把订阅拆成独立服务

订阅服务到期 → 调用订单服务下单 → 回调支付 → 再通知权益服务发放。
四跳里任何一跳超时/重复，就出现"钱收了会员没开通"或重复发放。**收益为零**：订阅没有独立数据、
没有独立扩缩容需求，它只是调度策略。

### 正例：允许的拆缝

- 积分账本独立模块（数据性质不同，负债只追加），与交易边界靠 `order.paid` 事件耦合（幂等，INV-15/26）；
- 认证独立（identity-system-builder）：只发 principal；
- 履约（发货/礼物）按事件消费，outbox 拆缝；
- 跨产品：共享代码模块（Go module），不共享运行实例——只有账号、收款流水这类物理唯一能力例外。

## 5. 拆分的"完成定义"

- 拆之前：画时间属性图 + 一致性边界图，写明收益；
- 拆之后：每个跨边界交互有事件、幂等键（选型见 MSP §10）、失败重试与对账入口；
- 验证：三个灵魂拷问全对 + 删表重建测试（权益删了能由流水重建）+ 重放测试（事件重放不重复发放）。
